핵심 역량

2011년부터 NC에서 클라이언트 프로그래머로 일하며 AOS, 슈팅, 대전 액션, 방치형까지 장르가 다른 네 개의 프로젝트를 거쳤습니다. 그중 둘은 상용 출시했고, 최근 프로젝트에서는 팀장을 맡아 업무 분배와 일정 관리를 함께 수행했습니다.

언리얼 엔진 심화 활용

Gamebryo에서 UE4로의 엔진 컨버팅을 거쳐 UE4·UE5를 실무에서 사용해 왔습니다. Slate 기반 에디터 확장, GameFeature, LevelSequence, AnimMontage·AnimNotify, PoseAsset, SceneCapture 등 필요한 엔진 기능을 목적에 맞게 선택해 씁니다.

멀티플레이어 전투 동기화

서버와 클라이언트의 권한 분배, 동기화 구조를 설계하고 개선해 왔습니다. 입력 반응성을 위해 클라이언트가 먼저 수행하고 서버가 검증하는 구조, RPC와 Replication의 선택 기준, 상태를 BitArray로 압축해 대역폭을 줄이는 방식까지 Dedicated Server 환경에서 다뤘습니다.

크로스 플랫폼 대응

PC, Android, iOS, 닌텐도 스위치, 게임패드까지 서로 다른 입력 체계와 빌드 환경을 하나의 코드베이스에서 다뤘습니다. 입력 처리를 계층 구조로 정리해 플랫폼별 분기를 최소화했습니다.

확장을 염두에 둔 시스템 설계

당장의 구현 편의보다 프로젝트가 커졌을 때 발생할 공수를 기준으로 구조를 정합니다. 전투 로직을 별개의 모듈로 분리해 서버 검증과 리플레이에 함께 쓰는 구조를 설계하거나, 컨텐츠를 GameFeature 단위로 나눠 운영 중 ON/OFF 할 수 있게 만든 사례가 있습니다.

개발 도구 · 파이프라인 구축

NodeEditor, Dialogue Editor, 리소스 분석기 등 기획·아트가 직접 사용하는 도구를 만들어 왔습니다. Jenkins 멀티 에이전트 빌드 파이프라인과 PSO 캐시 수집 자동화처럼, 팀 전체의 반복 작업을 줄이는 일에 관심이 많습니다.

AI를 붙인 개발 워크플로

Claude Code로 방치된 BP 그래프 노드가 있는 애셋을 검색하고, 자연어로 익스포트한 뒤 C++로 일괄 변환했습니다. 손이 많이 가지만 판단이 단순한 정리 작업을 AI에 넘기는 방식으로 활용합니다.

Panthera(블소 키우기)

NC 2024.11 — 2026.08 개발 중단

클라이언트 프로그래머 · 팀장

블레이드 앤 소울 IP를 활용한 방치형 키우기 게임. PC / Android / iOS 플랫폼으로 개발했으며, 보는 맛을 살린 액션성과 다양한 컨텐츠를 갖춘 키우기 게임을 지향했습니다.

Unreal Engine 5C++JetBrains RiderClaude CodePerforceJenkins

CommonUI 기반 UI 컨텐츠 작업

방치형 키우기 특성상 컨텐츠 대부분이 UI로 이루어져, 서로 다른 컨텐츠의 위젯이 동시에 열리고 겹치는 상황이 빈번했습니다. 컨텐츠별 UI가 서로를 가리거나 입력을 뺏지 않도록, 위젯의 표시 순서와 입력 우선순위를 공통 규칙으로 정리해야 했습니다.

  • ActivatableWidget을 활용하여 각 컨텐츠의 UI들을 타입에 맞게 레이어링
  • 게임 내에서 벌어질 수 있는 상황에 따라 각 ActivatableWidget 기반 위젯들을 적절한 레이어에 배치하도록 데이터 애셋 구성

신규 컨텐츠 UI는 데이터 애셋에 레이어만 지정하면 되어, 표시 순서와 입력 처리를 컨텐츠마다 개별 구현하지 않고 일관되게 가져갈 수 있게 되었습니다.

데이터 기반 전투 시스템 설계

전투 로직이 클라이언트에서만 동작하는 구조여서, 던전·스테이지가 끝날 때마다 서버가 결과를 별도로 검증해야 했습니다. 프로젝트가 진행될수록 검증 공수가 계속 커질 것으로 판단해, 서버와 클라이언트가 같은 전투 결과를 공유할 수 있는 구조로 바꿔야 했습니다.

  • 전투 로직을 독립 모듈로 분리하고, 같은 데이터를 주입하면 항상 같은 전투 결과가 나오도록 설계
  • 서버는 이 모듈을 검증과 리플레이 데이터 구성에 사용하도록 역할 정의
  • 클라이언트는 전투 이벤트를 받아 화면에 표현하는 역할만 담당하도록 경계 정의

전투 규칙을 데이터로 기술하고 서버와 클라이언트가 같은 모듈을 공유하는 구조를 설계로 확정했습니다. 서버는 검증과 리플레이, 클라이언트는 표현으로 역할 경계를 나눠 이후 구현이 따라갈 기준을 마련했습니다.

UE5 GameFeature 도입

프로그래머 한 명이 테이블 스키마 설계부터 서버 프로토콜 연동, 클라이언트 구현, UI까지 담당하는 팀 구조였고, 코드가 메인 모듈에 몰려 있어 모듈 간 의존성과 충돌을 줄이는 것이 중요했습니다. 컨텐츠를 서로 독립적으로 개발하면서, 운영 중에도 필요에 따라 켜고 끌 수 있는 구조가 필요했습니다.

  • 게임 핵심 로직 외의 컨텐츠(펫, 마법인형, 길드 등)를 각각 GameFeature Content로 분리
  • 이 구조를 적용하기 위해 메인 모듈에 몰려 있던 코드를 용도에 맞게 모듈 단위로 분리
  • 컨텐츠에 쓰이는 테이블 데이터와 리소스도 모듈 단위로 구분해 관리

컨텐츠 단위 ON/OFF가 운영 중 즉시 가능해졌고, 담당자별 작업 영역이 모듈 경계로 나뉘어 의존성과 충돌이 줄었습니다.

챕터별 보스전 개발 테이블 데이터와 시퀀스 애셋 추가만으로 신규 보스 확장

챕터마다 연출과 진행 규칙이 다른 보스전을 계속 추가해야 했습니다. 보스별 연출을 코드에 하드코딩하지 않고 데이터로 구성할 수 있어야 했습니다.

  • 보스전 전용 테이블 스키마 설계
  • 특정 Phase에 도달하면 전투를 멈추고 고유 레벨 시퀀스 재생, 부위 파괴, 전용 애니메이션 재생
  • 보스전 진입 시 사용하는 전용 Indicator UI 구현 및 연동

신규 보스를 테이블 데이터와 시퀀스 애셋 추가만으로 확장할 수 있는 형태로 정리했습니다.

인게임 컨텐츠 개발 성장·수집·경쟁 컨텐츠 5종 단독 완결, 렌더 타겟 1/3로 절감

방치형 게임 특성상 성장·수집·경쟁 축의 컨텐츠를 지속적으로 늘려야 했습니다. 각 컨텐츠를 데이터 설계부터 서버 연동, UI까지 한 사람이 완결해야 하는 역할을 맡았습니다.

  • 펫, 마법인형, 길드, 내공 시스템, 그룹 경쟁 시스템 등 개발
  • 데이터 테이블 구조 설계부터 서버 연동 프로토콜, 클라이언트 코드, 전용 UI 구현까지 진행
  • 그룹 경쟁 시스템은 랭커 3인의 메쉬를 위젯에 표시하기 위해 SceneCapture로 텍스처 한 장에 캡처한 뒤 머티리얼에서 3등분해 출력

서로 다른 축의 컨텐츠 다섯 종을 단독으로 완결했고, 랭커 표시는 캐릭터별 캡처 대신 한 장으로 묶어 렌더 타겟 수를 3분의 1로 줄였습니다.

캐릭터 FSM 개선 루트모션 상태이상의 이동 거리를 기획 데이터로 조절

상태이상의 종류가 늘어나면서, 하나의 State로 묶어 처리하던 방식으로는 각기 다른 동작을 표현하기 어려워졌습니다. 상태이상별 동작 차이를 코드 분기 대신 데이터로 제어할 수 있어야 했습니다.

  • 상태이상 State를 특성에 따라 세분화해 관리
  • 루트모션 기반 상태이상은 데이터 입력값에 따라 루트모션 길이를 제어하는 기능 추가

밀려남·띄우기처럼 루트모션을 쓰는 상태이상의 이동 거리를 기획 데이터로 조절할 수 있게 되었습니다.

UI 흐름 정리 및 일원화 활성 컨텐츠를 한 곳에서 판단해 컨텐츠별 예외 코드 제거

컨텐츠가 UI만으로 이루어지는 경우가 많은데, 현재 어떤 컨텐츠가 동작 중인지 알 수 있는 수단이 없어 컨텐츠 개발에 제약이 있음을 확인했습니다. 활성 컨텐츠를 한 곳에서 파악할 수 있도록 UI 진입 경로를 하나로 모아야 했습니다.

  • Widget Activate를 각 컨텐츠 코드에서 개별 호출하지 않고 ContentManager를 거치도록 정리
  • 이 클래스에서 활성 컨텐츠를 파악할 수 있도록 구현

중복 진입 차단이나 조건부 노출처럼 컨텐츠 간 상호작용이 필요한 처리를, 컨텐츠마다 예외 코드를 넣지 않고 한 곳에서 판단할 수 있게 되었습니다.

BP 그래프 노드를 C++ 코드로 일괄 변환 AI 로 애셋 약 200개를 C++ 로 이관, 디버깅 가능한 상태로

빠른 프로토타이핑용으로 만든 BP 그래프 노드가 장기간 방치되거나 편의상 계속 쓰이면서, 디버깅이 불편하고 코드 흐름 파악이 어려워지는 문제가 있었습니다. 대상 애셋이 많아 수작업으로 하나씩 옮기기에는 비용이 커, 정리 과정을 자동화할 방법이 필요했습니다.

  • Claude Code로 BP 그래프 노드가 있는 애셋을 검색
  • 노드를 자연어로 익스포트한 뒤, 그 파일을 C++ 코드로 변환하는 방식으로 정리

BP 그래프 노드가 방치돼 있던 애셋 약 200개를 C++ 코드로 옮겼습니다. 손이 많이 가지만 판단이 단순한 정리 작업을 AI에 넘긴 덕에, 흩어져 있던 로직이 C++로 모이면서 디버깅과 코드 추적이 가능한 상태가 되었습니다.

PSO 캐시 파이프라인 구성 수집을 자동화해 빌드마다 최신 PSO 캐시를 배포

모바일 플랫폼에서 셰이더가 최초 사용 시점에 컴파일되면서 발생하는 순간 끊김을 줄이려면 PSO 캐시가 필요했습니다. 게임에 등장하는 모든 레벨과 액터를 사람이 직접 돌며 수집하기는 어려워, 수집 과정 자체를 자동화해야 했습니다.

  • PSO 수집 전용 레벨을 구성
  • 스크립트로 게임에 등장하는 모든 레벨과 액터를 순차 스폰해 PSO를 수집한 뒤 배포에 활용

수집을 사람 손에서 떼어내, 빌드마다 최신 상태로 갱신된 PSO 캐시를 배포에 포함할 수 있게 되었습니다.

팀장 역할 수행 6명 규모 팀을 약 9개월, 컨벤션·코드 구조 가이드 정립

클라이언트 개발과 함께 6명 규모 팀의 팀장을 약 9개월간 맡아, 구현과 팀 운영을 병행했습니다. 프로그래머 한 명이 컨텐츠 하나를 처음부터 끝까지 담당하는 구조라, 업무와 일정을 나누는 것과 별개로 구현 방식이 담당자마다 갈라지지 않게 잡아줄 기준이 필요했습니다.

  • 팀원 업무 분배 및 일정 관리
  • 팀 코딩 컨벤션 정립
  • 팀원이 작성한 코드의 구조를 확인하고, 개선이 필요한 부분에 가이드 제시

컨벤션과 코드 구조 가이드를 팀의 공통 기준으로 세워, 컨텐츠마다 담당자가 다른 구조에서도 구현 방식이 갈라지지 않도록 했습니다.

Battle Crush

NC 2020.05 — 2024.10 2024.06 글로벌 출시

클라이언트 프로그래머

최대 30인이 동시에 전투하는 난투형 대전 액션 게임. 여러 플랫폼 간 크로스 플레이와 다양한 게임 모드를 제공했습니다. 2024년 6월 글로벌 출시 후 지금은 서비스 종료가 된 상태입니다.

지형 파괴 시스템 구현 — 초기 설계부터 전담

배틀 크러쉬 고유의 시스템으로, 게임 시작 시 랜덤하게 정해진 룰에 따라 지형이 무너지는 구조가 필요했습니다. 초기 설계부터 전담했습니다. 최대 30인이 동시에 전투하는 환경에서 모든 플레이어에게 지형 상태가 동일하게 보여야 했고, 그러면서 네트워크 사용량은 최소로 유지해야 했습니다.

  • 레벨 저장 시 각 지형에 ID를 부여하고, 서버가 정한 랜덤 시드를 클라이언트에 동기화한 뒤 파괴 웨이브 진행 룰을 결정, 서버와 클라이언트가 각자 웨이브를 진행하는 방식으로 시작
  • 캐릭터 행동 시스템과 동기화 방식이 달라 오차가 발생, 최종적으로는 서버가 웨이브 룰을 전담하고 지형의 낙하 여부가 바뀔 때마다 클라이언트로 Replication하는 구조로 변경
  • 이때 상태를 BitArray로 전송해 네트워크 사용량을 최소화

지형 상태의 서버–클라이언트 오차를 없애면서, 전송량은 지형당 비트 단위까지 압축했습니다. 게임의 핵심 차별 요소로 글로벌 출시까지 유지되었습니다.

재진입 프로세스 구현

인게임 진행 중 크래시 등으로 클라이언트가 종료되면, 진행 중이던 매치로 돌아갈 방법이 없었습니다. 재접속 시 원래 매치로 복귀할 수 있어야 했고, 이탈해 있는 동안에도 해당 캐릭터가 방치되지 않아야 했습니다.

  • 접속이 끊기면 해당 캐릭터를 AI Controller에 빙의시켜 Behavior Tree로 제어
  • 재접속 시 Dedicated Server에서 재진입 가능 여부를 검증
  • 문제가 없으면 캐릭터를 다시 PlayerController에 빙의시킨 뒤 필요한 정보를 RPC로 수신, 준비 완료를 확인하고 플레이를 재개

크래시나 네트워크 단절로 이탈해도 매치 복귀가 가능해졌고, 이탈 구간 동안 AI가 캐릭터를 대신 조작해 같은 팀의 플레이가 무너지지 않게 되었습니다.

전투 동기화 구조 개선 반응성은 선행 실행, 정확성은 서버 확정 후 실행으로 분리

난투형 대전 액션이라 입력 반응성과 액션성이 게임의 핵심인데, 서버 권한만으로 처리하면 반응이 늦어지는 구조적 제약이 있었습니다. 반응성과 서버 검증(신뢰성) 사이에서 액션별로 적절한 균형점을 잡아야 했습니다.

  • 입력 반응성과 액션성을 살리기 위해 유저 입력에 따른 액션을 클라이언트에서 먼저 수행하고 서버가 검증하는 구조로 구현
  • 검증에 성공하면 그대로 진행, 실패하면 Reject 후 클라이언트에 알려 후처리
  • 필요한 타이밍과 순서를 제어하기 위해 RPC를 사용하되, 전투 로직에 큰 영향을 주지 않는 범위에서 Replication을 병행
  • 이 방식이 버그를 유발한다는 의견이 있어, 일부 공격은 클라이언트가 요청하고 서버 검증이 끝난 뒤 알림을 받아 실행하는 형태로 변경

반응성이 중요한 액션은 선행 실행으로, 정확성이 중요한 공격은 서버 확정 후 실행으로 나눠, 체감 반응성과 검증 신뢰성을 동시에 확보했습니다.

레벨 프랍 배치 시스템 구성 레벨 저장 시 Validation 으로 배치 오류를 사전 차단

여러 레벨에 다양한 오브젝트가 배치되면서, 규격에서 벗어난 배치가 지형 파괴·전투 로직과 어긋나는 위험이 있었습니다. 프랍을 규격화하고, 잘못된 배치를 사람이 아니라 도구가 먼저 잡아내도록 만들어야 했습니다.

  • 레벨에 배치되는 모든 오브젝트를 직접 구현한 액터 클래스 기반 BP로만 배치하도록 제한해 프랍을 규격화
  • 프랍 종류별로 특성에 맞는 로직을 정의
  • 레벨 저장 시 맵 체크로 룰에 맞지 않는 프랍을 에디터에서 발견하고 수정할 수 있도록 Validation 기능 지원

규칙을 어긴 배치가 레벨 저장 시점에 에디터에서 바로 드러나, 런타임까지 넘어가던 배치 오류를 사전에 차단했습니다.

기존 캐릭터 리뉴얼 및 신규 캐릭터 구현 밸런스 조정이 기획자 선에서 가능해져 튜닝 사이클 단축

캐릭터마다 액션 구성이 달라, 캐릭터가 늘어날수록 개별 구현과 수정 비용이 함께 늘어나는 구조였습니다. 캐릭터 추가·수정 비용을 낮추고, 기획자가 데이터로 직접 조절할 수 있는 범위를 넓혀야 했습니다.

  • 유저 입력을 FSM 구조로 받아 State를 전이
  • AnimMontage의 커스텀 AnimNotify로 대미지 구간, 무적 구간 등 캐릭터별 이벤트를 기획자가 직접 데이터로 입력할 수 있도록 지원

대미지·무적 타이밍 같은 밸런스 조정이 프로그래머 수정 없이 기획자 선에서 가능해져, 캐릭터 튜닝 사이클이 짧아졌습니다.

  • 테이블 형태로 레벨 이벤트를 구성하는 전용 편집기를 별도 개발

리소스 현황을 엑셀로 공유할 수 있게 되었고, 레벨 이벤트는 노드 연결 대신 테이블 입력으로 제작하는 방식으로 전환했습니다.

자기소개서

안녕하세요, 14년차 게임 클라이언트 프로그래머 이윤석입니다.

저는 약 14년의 경력 동안 AOS, MMO Shooter, 난투 액션, 키우기류 게임까지 다양한 타이틀 개발에 참여했고, 이 중 2개의 작품은 출시까지 경험했습니다.

평소 콘솔 AAA급 타이틀 개발에 참여하고 싶은 열망이 있었고, 액션성 있는 게임들을 해보면서 각 게임의 타격 판정이나 콤보 시스템 구현에 대해 관심이 있었습니다. 실제로 제 커리어의 출시작 중 하나인 Battle Crush(난투 액션)에서 전투 시스템 전반의 구현과 데디서버 기반 전투 동기화를 집중적으로 담당하며 이 분야에 대한 실무 경험을 쌓아왔고, 그러던 중 NX3에서 Outant 프로젝트 공고를 보게 되어 새로운 도전의 기회라 생각해 지원하게 되었습니다.

길다면 나름 긴 시간동안 저는 클라이언트 프로그래머로서 역량을 잘 다져왔습니다. 제가 쌓아온 능력을 Outant 프로젝트를 위해 발휘해보고 싶습니다.

감사합니다.
